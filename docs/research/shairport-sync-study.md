## 2. Bonjour advertisement (classic RAOP)

- Service type: `_raop._tcp` default, overridable via `general.regtype` (`shairport.c:2046-2047`, `scripts/shairport-sync.conf:48`). Instance name is `<12 hex upper-case>@<service_name>`: built in `mdns.c:67-75` from `config.ap1_prefix[6]` printed `%02X` plus `@` plus `config.service_name`. Registered with `DNSServiceRegister(..., name, regtype, "", NULL, htons(port), txtlen, txt, ...)` on macOS (`mdns_dns_sd.c:58-72`), interface index optionally restricted (`mdns_dns_sd.c:66-68`).
- Where the prefix comes from: in a classic build it is **not** the MAC; it is the first 6 bytes of `MD5(service_name || hw_addr)` (`shairport.c:3634-3690`, `memcpy(config.ap1_prefix, ap_md5, 6)` at `:3686`). `hw_addr` is the first up/running non-loopback link-layer address (`common.c:2285-2350`, waits up to 10 s, warns if none). Release notes explain why: identical MAC-derived prefixes broke multiple instances (`RELEASENOTES.md:188`). In AirPlay 2 builds the prefix must equal the AP2 device id without colons (`shairport.c:1881-1894`, `RELEASENOTES.md:167`). Multi-instance hosts can derive a locally-administered FNV-1a hash of the name (`shairport.c:1855-1868`). Conclusion: iOS does not require a real MAC; it requires the prefix to be consistent with what the receiver puts into Apple-Response (section 3).
- TXT keys emitted in classic mode (`bonjour_strings.c:125-154`), in order: `sf=0x<statusflags>` (bit 17 "ReceiverSessionIsActive" set while a session holds the play lock, `rtsp.c:378-386`, cleared on release `rtsp.c:331-336`), `fv=<firmware>` (package version), `am=ShairportSync` (model), `vs=105.1`, `tp=TCP,UDP`, `vn=65537`, `md=0,1,2` or `md=0,2` (metadata types; 1 = artwork, omitted if cover art disabled), `ss=16`, `sr=44100`, `da=true`, `sv=false`, `et=0,1`, `ek=1`, `cn=0,1`, `ch=2`, `txtvers=1`, `pw=true|false`. No `pk` in classic mode; `pk` and `ft` appear only in the AirPlay-2-build variant (`bonjour_strings.c:85-115`). The legacy static table in `mdns.h:45-58` is the same set with `sf=0x4`, `fv=76400.10`. The RELEASENOTES note that AP2 builds adjusted the classic strings "so that it does not appear to provide MFi authentication" (`RELEASENOTES.md:134`).
- The source does not document which keys iOS requires. (inferred) `et`, `cn`, `tp`, `txtvers`, `ch/ss/sr` and the `@`-prefixed name are the ones historically needed; `md` only gates metadata/artwork; `pw` gates the Digest-auth prompt.
- Port: `config.port` defaults to 5000 in classic builds, 7000 for AP2 (`shairport.c:2990-3003`, `--port` help at `:341`). Fixed, not dynamic; bound on all addresses unless `general.address` set, IPv4 and IPv6 sockets with `IPV6_V6ONLY` (`rtsp.c:4333-4374`). Classic firewall list: 3689/tcp (DACP), 5353, 5000/tcp, 6000-6009/udp (`TROUBLESHOOTING.md:116-122`).

## 3. RTSP handshake

Parsing (`utilities/rtsp_message_utilities.c:163-220`): request line is `strtok`'d into method, path, version; version must be `RTSP/1.0` or `HTTP/1.1` (`:184`). Headers split on `": "` (exactly colon-space, `:195-203`). `Content-Length` via `atoi` (`:207`). Max 4096-byte header read buffer, grown to `Content-Length` (256 KiB pre-allocated when cover art is enabled, `rtsp.c:594-598`, `:694-703`). Header lookup is case-insensitive (`:111-117`). A packet without an RTSP-style request line gets `RTSP/1.0 400 Bad Request` and the connection stays open (`rtsp.c:4259-4274`).

Per-request common behaviour (`rtsp.c:4139-4210`): `apple_challenge()` runs on **every** request (`:4160`), `CSeq` is echoed (`:4161-4163`), `Server: AirTunes/105.1` is added (`:4169`), then password Digest auth if configured (`:4181`), then the method table (`:3635-3646`): OPTIONS, GET, POST, ANNOUNCE, FLUSH, TEARDOWN, SETUP, GET_PARAMETER, SET_PARAMETER, RECORD. Unknown methods get 501 (`:4149`). Response codes known: 200, 400, 403, 404, 451, 456, 470, 500, 501 (`rtsp.c:807-816`); 453 is set for "busy" but has no text table entry, so it is written as `453 Unauthorized` (`:819-828`, `:3608`). `Content-Length` is always written, even when 0 (`:852-856`). The whole reply must fit 4096 bytes minus 1024 slack (`:838-867`); it is written in one `write()` because Synology clients needed that (`RELEASENOTES.md:447`).

- **OPTIONS**: 200 with `Public: ANNOUNCE, SETUP, RECORD, PAUSE, FLUSH, TEARDOWN, OPTIONS, GET_PARAMETER, SET_PARAMETER` (`rtsp.c:2204-2213`).
- **Apple-Challenge → Apple-Response** (`rtsp.c:3648-3706`): base64-decode the challenge (Apple strips `=` padding; the decoder re-appends `===` before decoding, `common.c:634-650`); reject >16 bytes (`:3664`). Buffer of 48 zero bytes: challenge, then the **local socket address** from `getsockname` (4 bytes IPv4 or 16 bytes IPv6, `:3673-3684`), then the 6 `ap1_prefix` bytes (`:3686-3687`). If total < 32 it is zero-padded to 32 (`:3691-3692`). Signed with RSA PKCS#1 v1.5 padding and **no DigestInfo** ("a PKCS#1 v1.5 signature of the raw input", `common.c:905-907`; OpenSSL `EVP_PKEY_sign` with `RSA_PKCS1_PADDING` at `common.c:822-826`; mbedtls `MBEDTLS_MD_NONE` at `:997-1001`). Base64-encode and **strip trailing `=`** (`rtsp.c:3698-3701`).
- **ANNOUNCE** (`rtsp.c:3345-3609`): acquires the play lock (453 if refused, `:3608`). SDP body is scanned line by line (`nextline` accepts `\r`, `\n`, `\r\n`, `rtsp.c:432-452`) for `o=iTunes` (SSID, ignored), `a=rtpmap:96 L16/44100/2` (uncompressed PCM, `:3412-3419`), `a=fmtp:`, `a=aesiv:`, `a=aesiv`, `a=rsaaeskey:`, `a=min-latency:`, `a=max-latency:` (`:3404-3434`). Encryption is on iff **both** aesiv and rsaaeskey are present; one without the other is 456 (`:3461-3470`). `aesiv` must decode to 16 bytes; `rsaaeskey` is RSA-OAEP(SHA-1) decrypted and must yield 16 bytes (`:3472-3492`, `common.c:837-840` `RSA_PKCS1_OAEP_PADDING`, `:910` `PSA_ALG_RSA_OAEP(SHA_1)`). fmtp: 12 ints, defaults `96 352 0 16 40 10 14 2 255 0 0 44100`, overwritten by whitespace-separated `atoi` fields, bounded to 12 (`:3498-3520`, fix for crash on short fmtp `RELEASENOTES.md:337`); frames/packet = fmtp[1], rate = fmtp[11], channels = fmtp[7], bit depth = fmtp[3] (`:3527-3531`). If both L16 rtpmap and fmtp are present (pyatv/Home Assistant) the stream is PCM (`:3495-3497`). Headers read: `X-Apple-Client-Name` (`:3535`), `User-Agent` stored and `AirPlay/<n>` version parsed (`:3543-3558`); the version steers latency (section 5).
- **SETUP** (`rtsp.c:2980-3108`): 451 unless this connection owns the play lock (`:2987`). Reads `Active-Remote` and `DACP-ID` headers (`:2989-3026`). `Transport` is `strstr`'d for `control_port=` and `timing_port=` (`:3028-3041`); a duplicate SETUP with different ports warns (`:3043-3057`). Allocates three UDP sockets from `udp_port_base=6001`, range 10 (`shairport.c:2808-2809`, `common.c:345-486`; sockets bound to the connection's own local IP, scope id preserved for link-local IPv6). Reply: `Transport: RTP/AVP/UDP;unicast;interleaved=0-1;mode=record;control_port=%d;timing_port=%d;server_port=%d` and `Session: 1`, 200 (`:3069-3080`). No `Audio-Jack-Status` (commented out, `rtsp.c:4164`).
- **RECORD** (`rtsp.c:913-960`): starts the player thread (`player_play`), replies 200 with `Audio-Latency: 11025` (`:935`; comment at `:926-934` explains 77175+11025=88200 for old AirPlay, 88553+11025≈99578 for iTunes). `RTP-Info` `rtptime=` is treated as a flush-to point (`:942-953`). `seq=` is not parsed. Duplicate RECORD is ignored (`:917`).
- **FLUSH** (`rtsp.c:2299-2329`): parses `RTP-Info: ...rtptime=` with `uatoi`, calls `player_flush(rtptime)`; 451 if not the principal connection.
- **TEARDOWN** (`rtsp.c:2215-2234`): stops the player, replies 200 with `Connection: close`, sets `conn->stop`. The cleanup handler closes the three UDP sockets, frees DACP state, etc. (`rtsp.c:3944-4078`).
- **SET_PARAMETER** (`rtsp.c:3252-3343`): dispatch on `Content-Type`: `text/parameters` → lines `volume: <float>` (`atof`, `player_volume`) or `progress: <start>/<now>/<end>` (`rtsp.c:3116-3192`); `application/x-dmap-tagged` → DMAP walk starting at offset 8 (skips the `mlit` container header), each item `tag(4) len(4) value`, aborting if `len > remaining` (`rtsp.c:3194-3228`); `image/*` → raw body is the artwork, "the image/type tag isn't reliable" (`:3311-3330`). `RTP-Info: rtptime=` on these messages is used only as a correlation id (`:3263-3277`). Always 200.
- **GET_PARAMETER** (`rtsp.c:3230-3250`): if the body is exactly `volume\r\n`, replies `\r\nvolume: %.6f\r\n`; otherwise empty 200.
- Headers: `CSeq` echoed; `Session: 1` fixed; `DACP-ID`/`Active-Remote` captured at SETUP for remote control (section 8); `Client-Instance` is not referenced anywhere; `User-Agent` only for version sniffing. Password auth is RFC 2617 MD5 Digest with `realm="raop"`, 8-byte urandom nonce, 401 + `WWW-Authenticate` until correct (`rtsp.c:3720-3942`); password only works in classic mode (`ADVANCED TOPICS/InitialConfiguration.md:62`).
- iOS-version quirks: latency heuristics keyed on `AirPlay/<ver>` ≤353 (iOS 11.1.2) or ≥371 and on the sync-packet flags (`rtp.c:410-421`, `RELEASENOTES.md:413,479`); volume not restored after pause on iOS 11.2/macOS 10.13.2, so last volume is remembered (`RELEASENOTES.md:524`); "Whaale" sends unencrypted audio and returns resends on the control port (`RELEASENOTES.md:1252-1253`); iOS 9.2 sent teardown+new session back-to-back on track skip (`RELEASENOTES.md:977,1001,1029`); Mac browser audio needed careful player-lock handling (`RELEASENOTES.md:584`).

## 4. The RSA private key

- Location: `common.c:783-806`, `static char super_secret_key[]`, a 2048-bit PEM `BEGIN RSA PRIVATE KEY` block compiled into the binary; used for signing (`RSA_MODE_AUTH`) and key unwrap (`RSA_MODE_KEY`) in `rsa_apply()` (`common.c:810-900`, mbedtls variants `:903-1030`).
- Provenance: the tree carries **no** comment on where the key came from and no legal commentary; a grep for "AirPort Express", "extracted", "legal" near the key finds nothing. `README.md:51` only says Shairport Sync "is a fork of Shairport 1.0" by James Laird et al. The claim that this is the AirPort Express key extracted in 2011 is common knowledge outside this tree (inferred, not read here).
- Can Apple-Challenge be skipped? No. `apple_challenge()` is invoked unconditionally for every request that carries the header (`rtsp.c:4160`), independent of `et`. The TXT record advertises `et=0,1` (`bonjour_strings.c:137`) and the code accepts an unencrypted ANNOUNCE (`rtsp.c:3461-3464`; release note confirms a real client did this, `RELEASENOTES.md:1252`). But that only removes the OAEP key-unwrap; the challenge signature is sent by the client before ANNOUNCE and is answered regardless. The source has no path that returns a successful handshake without the private key: if `rsa_apply` fails the response is built from a NULL/zero-length buffer rather than omitted (`rtsp.c:3695-3703`). Whether iOS would accept a missing `Apple-Response` is not tested or documented in this tree. Design consequence: shipping a classic receiver that iOS devices will play to means shipping this key; the project must make its own call on that.

## 5. RTP audio path

- Sockets (`rtp.c:985-1098`): server/audio, control, timing, all UDP, bound to the local address of the RTSP connection. Client control and timing addresses are resolved from the client IP plus the SETUP ports. Three receiver threads: `rtp_audio_receiver`, `rtp_control_receiver`, `rtp_timing_receiver` (+ `rtp_timing_sender`).
- Audio packet (`rtp.c:225-290`): `type = packet[1] & ~0x80`; 0x60 audio, 0x56 resend reply (which has a 4-byte RTP-ish prefix skipped: `pktp += 4`, `:234-237`). Then standard 12-byte RTP header: seq at bytes 2-3, timestamp at 4-7, SSRC 8-11 (`:238`, `:263`), payload at +12. Payload < 16 bytes is dropped (`:274`); 0x56 with seq 0 is a "resend-related request packet", ignored (`:283`). Buffer is 2048 bytes (`:187`). Note the receiver does not check `plen >= 12` before reading the header (inferred risk; see section 11).
- Decryption (`player.c:1584-1616`): AES-128-CBC, key from ANNOUNCE, **IV reset to the ANNOUNCE `aesiv` for every packet** (`memcpy(iv, conn->stream.aesiv, 16)`, `:1587`), decrypt only `len & ~0xf` bytes, copy the trailing `len % 16` bytes through unchanged (`:1614`), no padding (`:1404`).
- ALAC decoding: three options. Hammerton `alac.c` (MIT, default without FFmpeg, "deprecated for security reasons as it is no longer maintained", `scripts/shairport-sync.conf:64-68`, `configure.ac:510-513`), Apple libalac (deprecated, `configure.ac:518-523`), FFmpeg (recommended, default when built with `--with-ffmpeg`, `configure.ac:469-472`). Hammerton decoder is configured from fmtp fields (`player.c:300-322`); the comment explains fmtp is laid out like Apple's `ALACSpecificConfig` (`player.c:224-290`). Each packet decodes to 352 frames of S16 stereo (`player.c:1620-1626`).
- Sequence handling (`player.c:1511-1565`): 16-bit `seq_t`, ring of `BUFFER_FRAMES=1024` slots indexed by `seqno % 1024` (`player.h:195`, `player.c:126`). First packet syncs `ab_read = ab_write = seqno`. If `seqno == ab_write` it is the expected packet; if `(int16_t)(seqno - ab_write) > 0` the gap slots are marked missing with `initialisation_time = now` and the write pointer jumps; if it is between `ab_read` and `ab_write` it is "late but usable"; else "too late" and counted (`:1555-1563`). Duplicates overwrite.
- Resend logic (`player.c:1735-1829`): after every received packet, walk from the first possibly-missing slot to `ab_write`; a missing slot qualifies for a request if it is not too early (`resend_control_first_check_time` 0.10 s since noticed), not too soon after the last request (`resend_control_check_interval_time` 0.25 s), and not too late (less than `resend_control_last_check_time` 0.10 s + backend buffer length before its play time, computed from `latency`) (`shairport.c:582-590`). Contiguous runs are coalesced into one request. Request packet (`rtp.c:1171-1200`): 8 bytes `0x80 0xD5 | seq(1) | first_missing(2) | count(2)`, sent to the client's control port; a sendto failure backs off 0.3 s (`:1203-1210`). Resent audio normally arrives on the audio port as 0x56; some clients return it on the control port as 0xD6 (`rtp.c:541-562`). Still-missing frames at play time are replaced by silence (`player.c:2810-2816`, `:3813-3837`).
- Sync packet (`rtp.c:325-537`): `packet[1] == 0xd4`; flags at bytes 2-3 (`0x0007` on iTunes, 4 on AirPlay; bit 0 "first" is not used separately — the whole 16-bit value is compared with 7, `:413`); bytes 4-7 "rtp timestamp less latency"; bytes 8-15 NTP time of the sync (32.32); bytes 16-19 rtp timestamp "now". Latency = `rt - rtlt` (`:409`), plus `fixedLatencyOffset = 11025` when flags==7 or AirPlay version ≤353 or ≥371 (`:413-416`, `shairport.c:572`), clamped by SDP min/max-latency and by `(3*1024*352)/4 - 11025` frames (`:423-431`), then adjusted by `audio_backend_latency_offset` (`:440-452`). The anchor (`anchor_rtptime = rt - latency`, `anchor_time = ntp`) is then set (`:498-502`). Sync packets are ignored until at least one timing reply has arrived (`:364`).
- Timing (`rtp.c:582-651`): the receiver sends 32-byte requests `0x80 0xd2 seq=7 filler origin=0 receive=0 transmit=0` every 0.3 s for the first three, then every 3 s. Replies `0xd3` carry receive (bytes 16-23) and transmit (24-31) in NTP 32.32 (`:744-765`). Round trips > 0.2 s are discarded (`:741`). Offset = `remote_transmit + rtt/2 - local_arrival` taken from the lowest-dispersion sample in a 128-entry history whose dispersions age geometrically (`player.h:116-118`, `rtp.c:788-840`). Drift: least-squares slope of remote vs local over "chosen" samples after a 60 s settling period and ≥8 points (`:862-928`); the gradient is remembered per client IP across sessions (`:654-688`, `:706-717`). `frame_to_local_time` converts via the anchor and the drift-corrected offset (`rtp.c:1119-1144`, `:156-174`).

## 6. Buffering and clock

- Buffer: 1024 slots × 352 frames ≈ 8.17 s (`player.h:183-195`, `shairport.c:591-594`). `minimum_free_buffer_headroom = 125` slots (`shairport.c:591`).
- Latency is **sender-imposed** through the sync packet (`rt - rtlt`), not through RECORD; the receiver's `Audio-Latency: 11025` reply is a fixed hint. The README states classic sources set "around 2.0 to 2.25 seconds" (`README.md:64`); the `-L/--latency` override is deprecated (`shairport.c:342`, `RELEASENOTES.md:1114`).
- `audio_backend_latency_offset_in_seconds` (default 0) shifts output earlier/later by a fixed amount (`scripts/shairport-sync.conf:89`, applied at `rtp.c:440-452`). `audio_backend_buffer_desired_length_in_seconds` (default 0.15 in code, 0.2 in sample conf; `shairport.c:2806`, conf `:93`) is how much audio to keep queued in the DAC; frames are released early by that amount and the player waits while `delay() >= desired` (`player.c:2690-2725`). `audio_backend_buffer_interpolation_threshold_in_seconds` 0.075 disables soxr when the DAC buffer gets low (conf `:97`).
- Start of play: the first frame's play time is computed and silence is sent from "now" until then ("silent lead-in", `player.c:2480-2650`, `shairport.c:568`); a late first frame skips frames instead (`player.c:4433-4466`).
- Keeping sync: every output block measures `sync_error = time_frame_will_play (from DAC delay) - time_it_should_play` (`player.c:4396-4411`); errors are kept in a 40-sample window, second-highest/second-lowest are averaged into a centered error (`:4559-4561`); if |centered| > `drift_tolerance_in_seconds` 0.002 the block is stuffed by ±(len/350) frames (`:4591-4607`, `INTERPOLATION_LIMIT=20`, `player.h:198`). Stuffing modes: `basic` (duplicate/drop a frame), `vernier` (default without soxr; weighted interpolation), `soxr` (libsoxr resample of the block by ±n frames), `auto` picks soxr if the CPU benchmark passes (`shairport.c:2797-2802`, `:297-301`, `player.c:2955-3300`).
- Resync: if |centered error| > `resync_threshold_in_seconds` 0.050 with a full 40-sample window not straddling zero, then either a resync (buffer re-anchored, silence lead-in redone) when early, or the late packet is dropped (`player.c:4634-4672`, `:2327-2348`). `resync_threshold = 0` disables (conf `:50`).
- Underrun: a missing slot becomes a 352-frame silent packet (`player.c:3813-3837`); a negative DAC delay is logged and treated as 0 (`:2706-2711`). Overrun/out-of-date packets whose timestamp is already past are dropped before release (`:2288-2321`). There is no fade in/out on start, stop or flush; "mute" means `-144` volume → hardware mute or `software_mute_enabled` (`player.c:5192-5208`), and dither is enabled whenever software attenuation is active (`:3772-3783`).
- Volume: `volume:` is -30..0 dB (`-144` mute, conf `:88`); mapped to the output range by `vol2attn` (3-segment curve, `common.c:1603-1650`), `flat`, or `dasl_tapered`; software gain is `65536 * 10^(dB/2000)` applied as a fixed-point multiplier (`player.c:5316-5327`). `GET_PARAMETER volume` returns the last volume so iOS resumes at the right level (`RELEASENOTES.md:524`).

## 7. Sessions

- One session at a time. A global `principal_conn` guarded by an rwlock is the "play lock" (`rtsp.c:355-430`). A second ANNOUNCE while another connection holds it returns **453** unless `allow_session_interruption` is on, in which case the old connection is terminated and the new one takes over (`rtsp.c:397-422`, `:3608`). In classic builds the listener additionally **closes the TCP connection immediately on accept** when busy and interruption is disallowed (`rtsp.c:4393-4399`), and otherwise grabs the lock at accept time (`:4577-4584`). AP2 builds always allow interruption in classic-compat mode (`rtsp.c:3351-3352`). Default `allow_session_interruption = "no"` (conf `:132`).
- Identification: by connection (TCP socket + thread), not by `Session` header (always "1"). DACP-ID/Active-Remote are per connection.
- Loss detection: no per-packet audio timeout in classic mode; TCP keepalive on the RTSP socket with idle = `session_timeout - 25` s, 5 probes at 5 s, so a vanished client is dropped after about `session_timeout` (default 60 s, minimum 60, 0 = never) (`rtsp.c:4404-4470`, `shairport.c:536-540`, `:2790`, `RELEASENOTES.md:174`). On ETIMEDOUT/EOF/read error the conversation thread stops, which runs the cleanup (stop player, close sockets, release lock) (`rtsp.c:614-640`, `:3944-4078`). A `-t 0` sets both no-timeout and allow-interruption (`shairport.c:1703-1708`, history at `RELEASENOTES.md:1300-1301`). `active_state_timeout` 10 s only delays the "inactive" hooks (`shairport.c:572`).

## 8. DACP remote control

- The sender advertises `_dacp._tcp` as `iTunes_Ctrl_<DACP-ID hex>`; shairport-sync browses that type and matches by stripping `iTunes_Ctrl_` and leading zeros against the `DACP-ID` from SETUP (`mdns_avahi.c:114-126`, `:169-178`); a `remove` event sets the port to 0 (`:177`). Only the Avahi backend implements the browser; the dns_sd backend has `mdns_dacp_monitor_* = NULL` (`mdns_dns_sd.c:146-151`), so on macOS a new implementation must write its own `DNSServiceBrowse/Resolve`. If no port is known the monitor re-asks every `missing_port_dacp_scan_interval_seconds` 2.0 (`shairport.c:588-589`, `dacp.c:523-525`).
- Request format (`dacp.c:249-253`): `GET /ctrl-int/1/<command> HTTP/1.1`, `Host: <ip>:<port>`, `Active-Remote: <value from SETUP>`, 0.5 s socket timeouts (`:228-234`), one conversation at a time. Commands used in the tree: `playpause`, `play`, `pause`, `stop`, `playresume`, `nextitem`, `previtem`, `beginff`, `beginrew`, `volumeup`, `volumedown`, `mutetoggle`, `getproperty?properties=dmcp.volume`, `setproperty?dmcp.volume=<0..100>`, `setproperty?include-speaker-id=<id>&dmcp.volume=<v>`, `setproperty?speaker-id=<id>&dmcp.volume=<v>`, `getspeakers`, `playstatusupdate?revision-number=1`, `nowplayingartwork?mw=320&mh=320` (`dacp.c:925-937`, `:1047`, `:1090-1100`, `:666`; command names via `remote/remote.c`, `dbus/dbus-service.c`, `mqtt.c`). Custom pseudo-status codes 490-498 for local failures (`dacp.c:170-181`). Long-polling is deliberately not used; revision-number is always 1 (`dacp.c:417-424`, `RELEASENOTES.md:135`). The RELEASENOTES describe the remote link as valid until the source deselects the receiver or disappears, and dropped after 15 minutes idle (`RELEASENOTES.md:508`); iOS exposes only the basic interface, iTunes the "advanced" one (`RELEASENOTES.md:343`).
- Metadata arrives via SET_PARAMETER DMAP (`core` tags such as `minm`, `asar`, `asal`, inferred from DMAP; the code just forwards tag+value) bracketed by `mdst`/`mden` carrying the `rtptime`; artwork arrives as a separate SET_PARAMETER with `Content-Type: image/...` and the raw bytes as body, bracketed by `pcst`/`pcen` (`rtsp.c:3279-3330`). `progress:` arrives as `start/now/end` RTP timestamps (`rtsp.c:3177-3184`). Clients also send `DACP-ID`/`Active-Remote` on every request, but only SETUP's copy is stored.

## 9. iOS / macOS compatibility

- The README calls classic AirPlay "the older, but still supported" protocol (`README.md:4`). `CONFIGURATION FLAGS.md:16` says classic AirPlay "offers multi-room operation to iTunes on macOS or Windows, the Music app on macOS and some third-party computer applications ... However, support for this version of AirPlay seems to be gradually waning. It does not offer multi-room operation to iOS, iPadOS or AppleTV and is incompatible with HomePod. It is not integrated with the Home app." Nothing in the tree says Apple has dropped AirPlay 1; `AIRPLAY2.md:62` says AP2 builds "can revert to 'classic' AirPlay if necessary". The AP2-build default `service_type = "auto"` offers AP2 when NQPTP is present, else classic with "(Classic)" appended (`scripts/shairport-sync.conf:28-31`). iTunes/Apple Music on Windows only work with the classic service (`TROUBLESHOOTING.md:80-87`, conf `:29`). "Macs based on Apple Silicon have built-in AirPlay facilities and so don't need Shairport Sync" (`README.md:11`). Classic AirPlay is 44.1 kHz/16-bit stereo ALAC only (`AIRPLAY2.md:63`); AP2 adds AAC, 48 kHz, 24-bit, surround, PTP timing via NQPTP on ports 319/320 (`AIRPLAY2.md:69-75`).
- Coexistence: classic uses TCP 5000 + UDP 6001-6010; the macOS AirPlay receiver (inferred) uses 7000 and the `_airplay._tcp` service, so port conflicts are not expected; the AP2 build notes that several AP2 instances can share an IP on distinct ports because "AirPlay 2 clients follow the SRV-advertised port, verified on iOS" (`shairport.c:2993-2997`, `AIRPLAY2.md:71`). The only hard conflict documented is NQPTP needing exclusive 319/320 (`AIRPLAY2.md:69`).

## 11. Defensive-parsing lessons

Documented past bugs: non-RTSP packets on port 5000 crashed the daemon (`RELEASENOTES.md:339`); incomplete `fmtp` crashed (`:337`); malformed RTSP packets stopped streaming (`:1352`); an `assert` on malformed data was removed (`:1063`); data-alignment crash in metadata on ARM (`:1002`, hence the `memcpy` at `rtsp.c:3205-3211`); tinysvcmdns heap overflow CVE-2017-12087 (`:556`); PCM copy heap overflow guarded in `player.c:203-209`; Hammerton and Apple ALAC are "deprecated for security reasons" (`configure.ac:513,523`). `SECURITY.md:36-39` declares RTSP/RTP, pairing, mDNS and metadata interfaces in scope.

Observed weak spots a new implementation should harden and unit-test:
1. Request line with fewer than three tokens, wrong version string, header without `": "`, header names >= struct limits (`msg_add_header` warns "too many headers?!", `rtsp_message_utilities.c:94-97`), non-numeric or negative `Content-Length` (`atoi`), absurd `Content-Length` (shairport-sync will `realloc` whatever is asked, `rtsp.c:694-703`; 15 s stall detection only).
2. `Apple-Challenge` not base64, empty, > 16 bytes, unpadded; `aesiv` of wrong length; `rsaaeskey` not 256 bytes or OAEP failure (`rsa_apply` returning NULL is `free`'d and `keylen` is uninitialised on the PSA path if parsing fails, inferred); SDP with `aesiv` but no `rsaaeskey`; fmtp with 0, 1, 20 fields, negative or zero frames-per-packet / rate / channels (shairport-sync does not sanity-check them, `rtsp.c:3521-3523`); SDP lines ending in `\r` only; missing final newline.
3. `Transport` without `control_port=`/`timing_port=`, port 0, port > 65535 (`atoi` unchecked); duplicate SETUP with different ports; SETUP/RECORD/FLUSH before ANNOUNCE (must be rejected, `rtsp.c:3104`, `:956`, `:2325`).
4. `RTP-Info` with missing `rtptime=`, `seq` only, or values ≥ 2^32 (`uatoi`); FLUSH before any audio (ignored, `player.c:1503-1508`).
5. SET_PARAMETER: `volume:` non-numeric or out of range (-144 must be honoured, values >0 or < -30 should clamp); DMAP body shorter than 8 bytes, item length exceeding the remainder (`rtsp.c:3214`), nested containers, zero-length items; multi-megabyte artwork; unknown `Content-Type`.
6. RTP: datagrams shorter than 12 (audio) or 16 (resend) bytes, shorter than 32 for timing replies and 20 for sync packets (shairport-sync reads fixed offsets without length checks, `rtp.c:368-376`, `:744-760`); payload not a multiple of 16; payloads > 2048; seq wraparound at 0xFFFF; packets whose decoded length is not 352 frames; timing replies arriving without a matching request; sync packets before any timing reply; absurd latency values (clamp like `rtp.c:425-431`); a 0x56 with sequence 0.
7. Resend storms: cap outstanding requests, rate-limit per slot, back off on sendto errors (`rtp.c:1203-1210`).
8. Concurrency: second TCP connection while playing (453 vs close), client sending TEARDOWN mid-FLUSH, RTSP EOF while the player thread is blocked on the DAC.

## 12. Design recommendations for a clean-room implementation

1. Advertise `_raop._tcp` as `<12HEX>@Name` with TXT `txtvers=1 ch=2 cn=0,1 et=0,1 ek=1 sr=44100 ss=16 tp=UDP vn=65537 da=true sv=false md=0,1,2 pw=false am=<model> vs=105.1 fv=... sf=0x4`; use the same 6 bytes for the name prefix and for the Apple-Response hwaddr field; a hash is fine, a real MAC is not required.
2. Keep RTSP on a fixed TCP port (5000 default, configurable) bound per interface, IPv4+IPv6; reply `Server: AirTunes/105.1`, echo `CSeq`, always send `Content-Length`.
3. Answer `Apple-Challenge` on **every** request: decode (tolerate missing `=`), build `challenge || local-IP(4|16) || hwaddr(6)` zero-padded to ≥32, sign RSA PKCS#1 v1.5 raw (no DigestInfo), base64 without `=`.
4. Treat the embedded RSA key as a product/legal decision made up front; the code path cannot avoid it for iOS senders.
5. OPTIONS → `Public: ANNOUNCE, SETUP, RECORD, PAUSE, FLUSH, TEARDOWN, OPTIONS, GET_PARAMETER, SET_PARAMETER`.
6. ANNOUNCE: parse SDP leniently; encryption iff both `aesiv` and `rsaaeskey`; RSA-OAEP-SHA1 unwrap to exactly 16 bytes; fmtp 12 ints with defaults; accept `L16/44100/2` PCM too; reject with 456 otherwise.
7. SETUP: allocate three UDP sockets on the connection's local address; reply `Transport: RTP/AVP/UDP;unicast;interleaved=0-1;mode=record;control_port=..;timing_port=..;server_port=..` and `Session: 1`.
8. RECORD → 200 + `Audio-Latency: 11025`, start the pipeline; honour `rtptime` as a flush point.
9. Start the NTP-style timing exchange immediately after SETUP (0.3 s x3 then 3 s), and ignore sync packets until the first timing reply.
10. Derive latency from sync packets (`rt - rtlt`, +11025 heuristic for flags==7 / version buckets), clamp to the buffer; do not hard-code 2 s.
11. Per-packet AES-128-CBC with the ANNOUNCE IV reset each packet; decrypt only `len & ~15`, copy the tail.
12. Decode to 352-frame S16 stereo blocks; a sequence-indexed ring of ≥1024 slots; silence for missing slots.
13. Resend requests: 8-byte `0x80 0xD5 seq first count` to the client control port, after 0.1 s, repeat every 0.25 s, stop 0.1 s before need; coalesce runs; accept resends on both audio (0x56, +4 offset) and control (0xD6) ports.
14. Clock model: lowest-dispersion offset selection plus least-squares drift after settling; convert rtptime→local time through the anchor.
15. Sync correction against the DAC's real delay: tolerance ~2 ms, stuff ±1 frame per ~350, resync beyond 50 ms; prime the DAC with silence before the first frame.
16. Keep 0.15–0.2 s in the DAC and release frames early by that amount.
17. Volume: -30..0 dB with -144 mute, curve to output range, answer `GET_PARAMETER volume`.
18. Single session with 453 for intruders unless interruption is enabled; TCP keepalive ≈60 s to detect vanished senders; also consider an audio-silence timeout.
19. On FLUSH drop buffered frames strictly before `rtptime`, reset the anchor logic and lead-in; on TEARDOWN close everything and re-advertise `sf` without the active bit.
20. DACP: browse `_dacp._tcp` for `iTunes_Ctrl_<DACP-ID>`, send `GET /ctrl-int/1/<cmd>` with `Active-Remote`; expect the service to vanish and reappear; use `dmcp.volume` for absolute volume.
21. Metadata: DMAP walk from offset 8 with strict bounds; artwork is the raw body of an `image/*` SET_PARAMETER; use `rtptime` to correlate.
22. Parse everything with explicit length checks (RTP ≥12/16/20/32 bytes, SDP, DMAP, Transport); fuzz the RTSP reader and RTP receivers first.
23. Test order: (a) Bonjour visible in iOS AirPlay picker; (b) OPTIONS/Apple-Response accepted (iOS proceeds to ANNOUNCE); (c) ANNOUNCE key unwrap; (d) SETUP/RECORD and first audio packet; (e) timing/sync lock and audible start within ~2 s; (f) FLUSH/track skip; (g) packet-loss injection and resend; (h) hour-long drift test against CoreAudio; (i) second-sender 453; (j) kill-the-phone keepalive teardown.
24. Keep the protocol core free of the platform: inject sockets, clock, mDNS, DAC delay; shairport-sync's pthread-cancel structure is the thing not to copy.
25. Reserve a sender-quirk table (User-Agent → latency rule, resend-on-control-port) rather than scattering `if`s as the original does.
